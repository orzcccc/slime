# 《史莱姆盲盒》Steam 端项目策划案

> 根据原始策划图片整理。本文保留原案中的玩法、数值与技术方案，并对层级和表述进行了结构化处理。

## 一、游戏总览（Game Overview）

### 核心定位

一款专为上班族设计的“桌面陪伴型”史莱姆收集与放置开箱游戏。

### 主界面形态

游戏以一座漂浮在桌面上的岛屿作为主界面，整个游戏固定只占约 `800×800` 的区域。窗口无边框、背景透明，岛屿以外能直接看到桌面；玩家可以按住岛屿把游戏拖到桌面上的任意位置。详细规则见 [桌面岛屿窗口系统](Systems/桌面岛屿窗口系统.md)。

### 核心体验

- 每天 3 分钟。
- 收集奇葩史莱姆。
- 剥离冗长养成。
- 主打极致的随机掉落爽感与图鉴收集癖。

### 开发平台

- Unity（PC 客户端）
- 微软 PlayFab（权威后端，正式版接入；开发阶段由客户端本地实现）
- Steamworks SDK（身份验证）

### 商业模式

F2P（免费游玩）+ 纯外观付费：

- 售卖培养皿皮肤
- UI 主题
- 特殊开箱特效
- 绝不售卖数值和抽卡次数

## 二、核心玩法系统（Core Gameplay）

### 1. 召唤法阵（核心资源获取）

#### 机制

游戏主界面是一个“史莱姆培养皿/召唤阵”。每隔 3 小时自动凝聚 1 个“史莱姆盲盒”，最多存储 8 个，可完整覆盖睡眠与上班时间。

#### 众生平等爆率

游戏时长不影响爆率：

- 80% 概率开出“基础史莱姆”，如水史莱姆、草史莱姆、泥巴史莱姆。
- 0.1% 概率开出全服唯一的“变异神话史莱姆”，如量子史莱姆、克苏鲁史莱姆。

### 2. 极简产出与对数养成（防数值膨胀）

#### 极简属性

史莱姆只有纯粹的“萌力值（CP）”或“粘液产出率”。

#### 对数成长

前期升级极快，后期极慢。老玩家享有积累优势，新玩家靠一次入魂的极品史莱姆可瞬间追平。

## 三、个人展柜（数字生态箱）

玩家拥有专属展柜，用于展示最稀有、最猎奇的史莱姆，并方便截图发群“装 X”。

## 四、Steam 端专属体验优化（Steam UX）

### 桌面陪伴模式

游戏默认以约 `800×800` 的透明无边框岛屿窗口常驻桌面，玩家可自由拖动位置，见 [桌面岛屿窗口系统](Systems/桌面岛屿窗口系统.md)。

原案中的“极简长条窗口”和吸附屏幕边缘（史莱姆在屏幕边缘蠕动，伪装成性能监控插件）是否作为附加模式保留，待确认。

### Steam 成就系统

设置海量成就，例如：

- 连续开出 100 个泥巴史莱姆
- 首次开出克苏鲁史莱姆

用于满足收集癖。

### Steam 丰富状态（Rich Presence）

好友列表显示类似“正在戳史莱姆——已累计开箱 1056 次”的状态，自带社交裂变效果。

## 五、技术架构（目标：Unity + Steamworks + PlayFab）

> 状态：目标架构已确定；开发阶段暂由客户端本地实现全部功能，见第六节。

原案要求“强联网”：客户端只负责表现，核心逻辑和资产放在云端，从根本上防止 Cheat Engine 等本地修改器作弊。正式版采用三端隔离架构：

- **Unity 客户端**：UI、史莱姆动画、开箱特效和本地显示数值；通过 Steamworks SDK 的 `GetAuthSessionTicket` 获取身份凭证完成免密登录。
- **Steamworks**：身份验证；若接入 Steam Inventory，也负责资产增减的验证。
- **PlayFab**：CloudScript 云函数负责计时、随机抽取和资产结算，并存储玩家数据。
- **Photon**：轻量实时消息，暂不启用。

详见 [目标后端架构](Systems/目标后端架构.md)。

## 六、开发阶段方案：客户端本地后端（已实现）

- 开发阶段所有功能由客户端处理，原 Node.js 自建服务端已删除，启动游戏不需要运行任何服务。
- 界面和控制器只通过后端接口 `IGameBackend` 读写数据；当前实现为本机计算并写入本地存档的 `LocalGameBackend`。
- 后端规则放在不依赖 Unity 的纯 C# 程序集中，切换到 PlayFab 时只需新增一个后端实现并修改工厂，规则代码可以迁移到 C# 云函数。
- 本地数据可以被本机修改，这是开发阶段接受的风险；正式发售前必须切换到 PlayFab + Steam 权威后端。

详见 [游戏后端与本地存档](Systems/游戏后端与本地存档.md)。

## 九、实现基线（当前采用方案）

> 状态：已确认，作为当前开发基线。后续若实现发生变化，应同步更新本节。

- **客户端**：Unity 2021.3 LTS、C#；Steam 插件（Facepunch.Steamworks 或 Steamworks.NET）待接入时确认。
- **后端**：开发阶段为客户端本地实现 `LocalGameBackend`，正式版为 PlayFab + Steam，两者实现同一个 `IGameBackend` 接口，返回相同的数据结构。
- **数据**：玩家数据保存为本地 JSON 存档，包含待领取盲盒与计时、盲盒仓库、史莱姆数量/等级/经验/首次获得时间；字段划分与未来 PlayFab User Data、Inventory 对应。
- **配置**：品质、盲盒、史莱姆目录、产出间隔和成长公式集中在 `GameBalanceConfig`，启动时校验；正式版迁移到 PlayFab Title Data / Catalog。
- **一致性**：每个修改操作在存档副本上完成，保存成功后才生效，失败时整体回滚。
- **测试**：后端规则由 `Assets/Tests/EditMode` 的 EditMode 测试覆盖，时间和随机数可注入，结果可确定复现。

接口列表、存档格式、容错规则和迁移步骤见 [游戏后端与本地存档](Systems/游戏后端与本地存档.md)。

## 十、本地最小可玩闭环（已实现）

> 当前阶段暂不接入真实 Steam，使用固定的本地玩家档案。正式 Steam 登录、成就与 Rich Presence 暂缓。

### 1. 盲盒生成与状态模型

- 新玩家初始拥有 1 个待领取盲盒。
- 每 3 小时生成 1 个盲盒，默认容量为 8 个；读取游戏状态、领取或开箱前按当前时间结算离线产出。
- 达到容量上限后停止累计，并将计时基准推进到本次结算时间，防止玩家领取后一次性获得溢出的历史盲盒。
- 到达下一个盲盒的产出时间时，客户端自动同步一次状态。
- 开箱必须消耗 1 个仓库盲盒；扣箱、随机抽取、库存入账和 CP 更新一次性保存。

### 2. Unity 原型框架

- 启动场景后由运行时 Bootstrap 自动创建游戏控制器、主界面和桌面窗口控制器；控制器通过 `GameBackendFactory` 获得当前后端并自动登录本地玩家。
- 原型界面包含玩家 CP、盲盒数量与倒计时、领取与开箱、库存列表和操作反馈。
- 当前 UI 已统一使用 `TextMeshProUGUI` 与项目内 `KeinannMaruPOP SDF` 动态字体资产；占位色块和正式视觉动画仍在核心闭环稳定后逐步替换，详见 [最小 UI 框架](Systems/UI框架.md)。

### 3. 本阶段验收标准

- Unity 进入 Play Mode 后自动登录本地玩家，不需要启动任何服务。
- 玩家可以领取初始盲盒并开箱，结果立即出现在库存和图鉴中；重启游戏后数据保留。
- 仓库无对应盲盒时拒绝开箱；离线产出按 3 小时周期结算且不超过 8 个。
- 后端计时、容量封顶、保存失败回滚和开箱概率可通过注入时间及随机数进行确定性自动化测试。

### 4. 后续需求队列

1. 史莱姆等级与对数成长的培养来源。
2. 个人展柜。
3. 接入 PlayFab + Steam 权威后端，正式 Steam Ticket 鉴权、成就与 Rich Presence。

## 十一、养成与图鉴（已实现）

### 1. 史莱姆成长数据

- 每个史莱姆类型记录数量、等级、经验和首次获得时间。
- 单只史莱姆有效 CP 为 `floor(基础 CP × (1 + log2(等级) × 0.25))`，总 CP 根据所有库存数量和等级由后端实时计算。
- 当前保留等级与经验字段用于后续成长系统。

### 2. 图鉴

- 开箱首次获得史莱姆时自动解锁图鉴并记录首次获得时间。
- 图鉴返回全部配置、发现状态、首次获得时间和完成度；未发现条目在客户端显示为 `???`。

### 3. 本地 GM 工具

- 开发阶段正式打包的游戏也显示 GM，由 `GameBackendFactory.DeveloperToolsEnabled` 统一控制；对外发售前关闭。
- 支持增加盲盒、填满、清空和推进盲盒计时；增加数量限制为 1—100，推进时间限制为 1—168 小时。
- Unity “培养皿/GM”页提供 `+1`、`+8`、填满、清空和推进 3 小时按钮，用于快速测试开箱流程。

### 4. 当前客户端页面

- 培养皿/GM
- 背包与史莱姆库存
- 图鉴及完成度
- 盲盒仓库与开箱

当前运行时原型使用 `TextMeshProUGUI`，字体统一为由项目内荆南麦圆体（`Assets/Resources/Fonts/KeinannMaruPOP.ttf`）生成的动态 SDF 资产（`Assets/Resources/Fonts/KeinannMaruPOP SDF.asset`），不再依赖 Windows 系统字体。正式发布前需核验该字体的商用与再分发授权。

#### 临时像素视觉方案

- 原型阶段复用项目内 `Pixel Adventure 2` 的史莱姆序列帧作为培养皿动态主视觉。
- UI 使用深蓝紫背景、紫色像素边框和绿色高亮按钮，统一培养皿、页签、库存与 GM 面板的临时视觉语言。
- 运行时保持整数感较强的边框和色块，不对低分辨率角色素材做背景式拉伸。
- 该素材仅作为开发阶段视觉占位；正式商业发布前必须再次核对素材授权，并替换为项目自有的史莱姆、图标和 UI 套件。

#### UI Prefab 资源化方案

- 当前主界面采用明亮圆润、角色中心的卡片式布局：顶部玩家/资源栏、中央培养皿主视觉、独立功能页和底部四项导航。
- 主界面保存为真实 Unity Prefab：`Assets/Resources/UI/MainUI.prefab`。
- 界面不再通过 Unity Editor 修改，统一直接修改预制文件，规则见 `.cursor/rules/unity-prefab-authoring.mdc`；不使用生成器重建。
- 可跨页面复用的按钮、遮罩、标签和卡片统一优先使用 `Assets/Resources/UI/Common/` 下的公共 Prefab；新增 UI 时先检索公共资源，缺失且符合公共组件标准时先建立公共 Prefab。
- 运行时通过 `Resources.Load<GameObject>("UI/MainUI")` 加载 Prefab；代码仅负责绑定接口数据、按钮事件、动态列表项和史莱姆动画，不再拼装整套静态页面。
- 页面包含主页、库存养成、盲盒与图鉴；GM 工具位于主页侧卡片，开发阶段所有构建均可用。
- 当前采用 `Resources` 便于原型快速迭代；资源规模扩大或需要热更新时再迁移到 Addressables。
- 背包已按效果图重做为独立弹窗 `InventoryPopup.prefab`：每页 4×2 张品质卡、排序与品质筛选、史莱姆详情，详见 [背包与物品界面](Systems/背包与物品界面.md)，切图见 [背包切图资源](Systems/背包切图资源.md)（占位美术）。
- 项目自有 `Resources/icon` 图片已用于底部导航、功能弹窗和五档盲盒外观；盲盒图片随品质数据动态切换，不改变后端抽取规则。
- UI 框架与看图生成预制的规则已确定：参考分辨率 `800×800`、match `0.5`、场景唯一 Canvas、TextMeshPro。现有界面待逐步迁移，详见 [最小 UI 框架](Systems/UI框架.md) 和 [预览图生成 UI 预制规则](Systems/预览图生成UI预制规则.md)。
- 主界面已按第二版效果图换图（蓝色调岛屿、深色面板、圆形功能按钮），节点结构不变，切图在 `Assets/Resources/Sprites/MainPage/`，属于占位美术，详见 [主界面切图资源](Systems/主界面切图资源.md)。
- 岛屿主界面（M01）已按线框图和效果图重做：顶部总 CP 与展示开关，岛上凝聚台显示待领取槽位、产出计时与领取按钮，底部功能坞为仓库、背包、图鉴、设置，详见 [岛屿主界面](Systems/岛屿主界面.md)。

#### 游戏设置

- 主界面顶栏提供设置入口，设置弹窗以独立 `GameSettings.prefab` 动态加载。
- 游戏固定为 `800×800` 桌面岛屿窗口，设置弹窗不再提供显示模式和分辨率选项，只保留拖动提示和退出游戏。

## 十三、盲盒领取、仓库与品质（已实现）

挂机区每 3 小时生成 1 个待领取盲盒，默认最多积累 8 个；玩家点击领取后，盲盒逐个随机为白、绿、蓝、紫、红五种品质并转入无上限仓库，可长期保存。开启时由玩家指定仓库中的盲盒品质，越稀有的盲盒会提高高品质史莱姆的相对抽取权重。

完整领取概率、品质加权公式、处理流程和验收标准见：

## 十五、桌面岛屿窗口（已实现）

主界面是一片岛屿，整个游戏固定占用 `800×800` 的桌面区域。窗口无边框、背景透明，岛屿外的透明区域点击穿透到桌面；玩家按住岛屿即可把游戏拖到桌面任意位置，位置在重启后保留，且不会被拖出屏幕。游戏只有这一种显示形态，不再提供全屏和分辨率切换。窗口能力只在 Windows Player 构建中生效。
