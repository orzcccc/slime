# 《史莱姆盲盒》Steam 端项目策划案

> 根据原始策划图片整理。本文保留原案中的玩法、数值与技术方案，并对层级和表述进行了结构化处理。

## 一、游戏总览（Game Overview）

### 核心定位

一款专为上班族设计的“桌面陪伴型”史莱姆收集与放置开箱游戏。

### 主界面形态

游戏以一座漂浮在桌面上的岛屿作为主界面，整个游戏固定只占约 `800×800` 的区域。窗口无边框、背景透明，岛屿以外能直接看到桌面；玩家可以按住岛屿把游戏拖到桌面上的任意位置。详细规则见 [桌面岛屿窗口系统](Systems/桌面岛屿窗口系统.md)。

### 核心体验

- 每天 3 分钟。
- 收集奇葩史莱姆。
- 剥离冗长养成。
- 主打极致的随机掉落爽感与图鉴收集癖。

### 开发平台

- Unity（PC 客户端）
- 轻量级云服务器（权威后端）
- Steamworks SDK（身份验证）

### 商业模式

F2P（免费游玩）+ 纯外观付费：

- 售卖培养皿皮肤
- UI 主题
- 特殊开箱特效
- 绝不售卖数值和抽卡次数

## 二、核心玩法系统（Core Gameplay）

### 1. 召唤法阵（核心资源获取）

#### 机制

游戏主界面是一个“史莱姆培养皿/召唤阵”。每隔 3 小时自动凝聚 1 个“史莱姆盲盒”，最多存储 8 个，可完整覆盖睡眠与上班时间。

#### 众生平等爆率

游戏时长不影响爆率：

- 80% 概率开出“基础史莱姆”，如水史莱姆、草史莱姆、泥巴史莱姆。
- 0.1% 概率开出全服唯一的“变异神话史莱姆”，如量子史莱姆、克苏鲁史莱姆。

### 2. 极简产出与对数养成（防数值膨胀）

#### 极简属性

史莱姆只有纯粹的“萌力值（CP）”或“粘液产出率”。

#### 对数成长

前期升级极快，后期极慢。老玩家享有积累优势，新玩家靠一次入魂的极品史莱姆可瞬间追平。

## 三、个人展柜（数字生态箱）

玩家拥有专属展柜，用于展示最稀有、最猎奇的史莱姆，并方便截图发群“装 X”。

## 四、Steam 端专属体验优化（Steam UX）

### 桌面陪伴模式

游戏默认以约 `800×800` 的透明无边框岛屿窗口常驻桌面，玩家可自由拖动位置，见 [桌面岛屿窗口系统](Systems/桌面岛屿窗口系统.md)。

原案中的“极简长条窗口”和吸附屏幕边缘（史莱姆在屏幕边缘蠕动，伪装成性能监控插件）是否作为附加模式保留，待确认。

### Steam 成就系统

设置海量成就，例如：

- 连续开出 100 个泥巴史莱姆
- 首次开出克苏鲁史莱姆

用于满足收集癖。

### Steam 丰富状态（Rich Presence）

好友列表显示类似“正在戳史莱姆——已累计开箱 1056 次”的状态，自带社交裂变效果。

## 五、技术架构与落地路线（Unity + 轻量级权威后端）

> 当前开发阶段使用本节和第九节的 Node.js 自建权威后端流程。远期计划替换为“胖客户端 + 瘦服务端”的三端架构：Unity 负责表现和本地数值计算，Steamworks 负责身份和资产，PlayFab 负责云端校验和数据存储，Photon 负责轻量实时消息。详见 [目标后端架构](Systems/目标后端架构.md)。

### 核心架构说明

既然直接采用方案二，应使用“强联网”架构：

- 客户端仅作为“播放器”。
- 所有核心逻辑和数据资产全部存放在云服务器。
- 从根本上封堵 Cheat Engine（CE）等本地修改器作弊的可能。

### 客户端（Unity PC 端）

职责：

- UI 渲染。
- 史莱姆动画播放（Spine 或 2D 骨骼）。
- 开箱特效展示。
- 接入 Steamworks SDK。
- 仅调用 `GetAuthSessionTicket` 获取玩家的 Steam 身份凭证，并发送给服务端完成免密登录。

### 轻量级服务器（权威后端）

#### 推荐技术栈

- Node.js（或 Go）
- Redis（缓存与队列）
- MySQL（持久化数据）

原案备注：作为前端开发者，Node.js 上手后端最快。

#### 核心职责

1. **账号与鉴权**：验证 Steam Ticket，绑定玩家数据。
2. **权威计时与 RNG**：在服务器端计算盲盒产出时间；所有“开箱随机数生成”均在服务端执行，仅将最终结果（抽到了什么史莱姆）下发给 Unity。

## 六、建议的下一步行动

由于已选定接入厂商方案二，建议暂时不要先制作 UI，而是优先跑通技术骨架：

1. **跑通鉴权流程**：Unity 中获取 Steam Ticket，并发送给本地跑起来的 Node.js 服务器，完成“Steam 一键登录”的闭环。
2. **编写并衔接口**：在 Node.js 中编写一个简单的 `/api/openBox` 接口，实现基于权重的随机抽取逻辑，并返回一个史莱姆 ID。
3. **Unity 联调**：在 Unity 放置一个简陋按钮，点击调用接口，并在 Console 打印抽到的史莱姆 ID。

完成以上三步后，项目的核心技术地基即搭建完成，之后可继续堆叠美术表现和史莱姆图鉴。

## 九、全栈实现基线（当前采用方案）

> 状态：已确认，作为当前开发基线。后续若实现发生变化，应同步更新本节。

### 1. 技术栈与通信约定

- **Unity 客户端**：Unity 2021.3 LTS、C#、Facepunch.Steamworks 或 Steamworks.NET（Steam 插件最终选型待接入时确认）。
- **后端服务**：Node.js + Express。
- **数据库**：开发阶段使用 SQLite，降低本地开发与部署成本；上线阶段预留迁移至 MySQL 的能力。
- **数据访问**：使用 `sqlite3`；业务代码通过独立仓储层访问数据库，避免 SQLite 逻辑散落在路由中。
- **通信协议**：HTTP RESTful API + JSON。
- **登录状态**：服务端签发 JWT；需要登录的接口必须携带 `Authorization: Bearer <JWT_TOKEN>`。
- **权威原则**：开箱、库存变更和 CP 统计均由服务端计算并以事务方式落库，Unity 不决定随机结果。

### 2. 核心数据模型

#### Users（玩家表）

- `id`：自增主键。
- `steam_id`：Steam ID 字符串，唯一索引。
- `nickname`：玩家昵称。
- `total_cp`：玩家总萌力值。
- `created_at`、`last_login_at`：创建与最后登录时间。

#### Slime_Dictionary（史莱姆配置字典，只读）

- `slime_id`：整数主键。
- `name`：史莱姆名称。
- `rarity`：稀有度，当前使用 `N/R/SR/SSR/UR`。
- `base_cp`：基础萌力值。
- `drop_weight`：服务端开箱权重；权重必须为非负整数。

#### User_Inventory（玩家史莱姆库存）

- `id`：自增主键。
- `user_id`：关联 Users。
- `slime_id`：关联 Slime_Dictionary。
- `quantity`：拥有数量，必须为非负整数。
- `(user_id, slime_id)` 建立唯一约束，避免同一史莱姆产生重复库存行。

### 3. 第一阶段 API 契约

#### `POST /api/auth/login`

- 请求：`{ "steamTicket": "hex_string" }`
- 返回：`{ "token": "jwt_string", "user": { "steam_id": "...", "nickname": "..." } }`
- 正式环境由后端调用 Steam Web API `ISteamUserAuth/AuthenticateUserTicket` 验票。
- 本地开发允许显式开启开发登录模式，但生产环境不得接受伪造票据。

#### `POST /api/game/open-box`

- 需要 JWT。
- 服务端按 `drop_weight` 进行加密安全随机抽取，并自动写入库存。
- 返回：`{ "slime_id": 101, "name": "水史莱姆", "rarity": "R" }`。

#### `GET /api/user/inventory`

- 需要 JWT。
- 返回当前玩家拥有的全部史莱姆及数量。

### 4. Steam 鉴权工作流

1. Unity 调用 Steamworks API 获取当前玩家的 `AuthSessionTicket`，转换成十六进制字符串。
2. Unity 将 Ticket 提交至 `POST /api/auth/login`。
3. Node.js 使用 Steam Web API Key 请求 `ISteamUserAuth/AuthenticateUserTicket`。
4. 验证成功后取得可信 SteamID；数据库中不存在则注册，存在则更新昵称及最后登录时间。
5. Node.js 签发 JWT 返回 Unity，Unity 在后续请求中通过 Bearer Header 携带。

### 5. 安全与验收约束

- `JWT_SECRET`、Steam Web API Key、Steam App ID 仅从环境变量读取，不写入代码仓库。
- 登录接口必须限制请求频率；错误响应不得泄露密钥、SQL 或内部堆栈。
- 开箱仅允许选择 `drop_weight > 0` 的配置；总权重无效时拒绝请求。
- 库存扣减、开箱奖励和总 CP 更新必须具备原子性，失败时全部回滚。
- 当前尚未配置 Steam App ID、Web API Key 与 Unity Steamworks 插件；在配置完成前，真实 Steam 验票不视为完成。

## 十、本地最小可玩闭环（已实现）

> 当前阶段暂不接入真实 Steam，固定使用仅在非生产环境启用的 `dev:<玩家标识>` 登录。正式 Steam 环境、养成、图鉴和社交系统均暂缓。

### 1. 盲盒生成与状态模型

- 新账号初始拥有 1 个盲盒，便于立即完成本地联调。
- 每 3 小时由服务端生成 1 个盲盒，默认容量为 8 个。
- 服务端保存 `box_count`、`box_capacity` 和 `last_box_at`；读取游戏状态或开箱前按服务器时间结算离线产出。
- 达到容量上限后停止累计，并将计时基准推进到本次结算时间，防止玩家开箱后一次性获得溢出的历史盲盒。
- `GET /api/game/state` 返回盲盒数量、容量、总 CP、服务器时间和下一盲盒生成时间。
- 开箱必须消耗 1 个已生成盲盒；扣箱、随机抽取、库存入账和 CP 更新位于同一数据库事务。

### 2. Unity 本地原型框架

- 启动场景后由运行时 Bootstrap 自动创建 `SlimeApiClient`、应用状态控制器和 uGUI 原型界面。
- 自动使用 `dev:local-player` 登录，并拉取游戏状态与库存。
- 原型界面包含玩家 CP、盲盒数量与倒计时、开箱按钮、库存列表和操作反馈。
- 当前 UI 使用 TextMeshPro 与占位色块，不依赖正式美术；正式视觉和动画在核心闭环稳定后替换。

### 3. 本阶段验收标准

- 本地后端启动后，Unity 进入 Play Mode 可自动登录开发账号。
- 玩家可以消耗初始盲盒开箱，结果立即出现在库存中。
- 无盲盒时服务端拒绝开箱；离线产出按 3 小时周期结算且不超过 8 个。
- 后端计时、容量封顶、事务回滚和开箱概率可通过注入时间及 RNG 进行确定性自动化测试。

### 4. 后续需求队列

1. 史莱姆等级与对数成长的培养来源。
2. 史莱姆图鉴、首次获得状态及收集完成度。
3. 个人展柜。
4. 正式 Steam Ticket 鉴权、成就与 Rich Presence。

## 十一、养成与图鉴（已实现）

### 1. 史莱姆成长数据

- 每个史莱姆类型记录数量、等级、经验和首次获得时间。
- 单只史莱姆有效 CP 为 `floor(基础 CP × (1 + log2(等级) × 0.25))`，总 CP 根据所有库存数量和等级由服务端重算。
- 当前保留等级与经验字段用于后续成长系统。

### 2. 图鉴

- 开箱首次获得史莱姆时自动解锁图鉴并记录首次获得时间。
- 图鉴返回全部配置、发现状态、首次获得时间和完成度；未发现条目在客户端显示为 `???`。

### 3. 本地 GM 工具

- GM 接口仅在非生产环境且开启开发登录时注册，生产环境直接不存在。
- 仅 `dev_` 开发账号的有效 JWT 可操作当前账号。
- 支持增加盲盒、填满、清空和推进盲盒计时；增加数量限制为 1—100，推进时间限制为 1—168 小时。
- Unity “培养皿/GM”页提供 `+1`、`+8`、填满、清空和推进 3 小时按钮，用于快速测试开箱流程。

### 4. 当前客户端页面

- 培养皿/GM
- 背包与史莱姆库存
- 图鉴及完成度
- 盲盒仓库与开箱

当前运行时原型使用 uGUI `Text` 和 Windows 系统中文字体；正式发布前需导入具备商业授权的中文字体资产。

#### 临时像素视觉方案

- 原型阶段复用项目内 `Pixel Adventure 2` 的史莱姆序列帧作为培养皿动态主视觉。
- UI 使用深蓝紫背景、紫色像素边框和绿色高亮按钮，统一培养皿、页签、库存与 GM 面板的临时视觉语言。
- 运行时保持整数感较强的边框和色块，不对低分辨率角色素材做背景式拉伸。
- 该素材仅作为开发阶段视觉占位；正式商业发布前必须再次核对素材授权，并替换为项目自有的史莱姆、图标和 UI 套件。

#### UI Prefab 资源化方案

- 当前主界面采用明亮圆润、角色中心的卡片式布局：顶部玩家/资源栏、中央培养皿主视觉、独立功能页和底部四项导航。
- 主界面保存为真实 Unity Prefab：`Assets/Resources/UI/MainUI.prefab`，可在 Inspector 和 Prefab Mode 中直接调整。
- Prefab 由 Unity Editor API 的 `PrefabUtility.SaveAsPrefabAsset` 创建；编辑器菜单 `Slime/UI/Rebuild Main UI Prefab` 可重新生成基线布局。
- 运行时通过 `Resources.Load<GameObject>("UI/MainUI")` 加载 Prefab；代码仅负责绑定接口数据、按钮事件、动态列表项和史莱姆动画，不再拼装整套静态页面。
- 页面包含主页、库存养成、盲盒与图鉴；GM 工具位于主页侧卡片，仅开发环境服务端允许执行。
- 当前采用 `Resources` 便于原型快速迭代；资源规模扩大或需要热更新时再迁移到 Addressables。
- 当前界面使用 `Sweet Land GUI` 的九宫格边框、按钮和设置图标统一卡片视觉；背包网格按容器宽度自动调整列数，内容高度按实际行数计算，详细规范见 [背包与物品界面](Systems/背包与物品界面.md)。
- 项目自有 `Resources/icon` 图片已用于底部导航、功能弹窗和五档盲盒外观；盲盒图片随品质数据动态切换，不改变服务端抽取规则。

#### 游戏设置

- 主界面顶栏提供设置入口，设置弹窗以独立 `GameSettings.prefab` 动态加载。
- 游戏固定为 `800×800` 桌面岛屿窗口，设置弹窗不再提供显示模式和分辨率选项，只保留拖动提示和退出游戏。
- 详细结构和验收标准见 [游戏设置系统](Systems/游戏设置系统.md)。

## 十三、盲盒领取、仓库与品质（已实现）

挂机区每 3 小时生成 1 个待领取盲盒，默认最多积累 8 个；玩家点击领取后，盲盒逐个随机为白、绿、蓝、紫、红五种品质并转入无上限仓库，可长期保存。开启时由玩家指定仓库中的盲盒品质，越稀有的盲盒会提高高品质史莱姆的相对抽取权重。

## 十五、桌面岛屿窗口（已实现）

主界面是一片岛屿，整个游戏固定占用 `800×800` 的桌面区域。窗口无边框、背景透明，岛屿外的透明区域点击穿透到桌面；玩家按住岛屿即可把游戏拖到桌面任意位置，位置在重启后保留，且不会被拖出屏幕。游戏只有这一种显示形态，不再提供全屏和分辨率切换。窗口能力只在 Windows Player 构建中生效。
