# 目标后端架构（胖客户端 + 瘦服务端）

> 状态：规划中（远期目标架构，当前不实现）  
> 最后更新：2026-11-05  
> 主策划入口：[《史莱姆盲盒》项目策划案](../史莱姆盲盒-项目策划案.md)

## 一、与当前方案的关系

- **当前开发阶段**：继续使用现有流程，即 Unity 客户端 + Node.js/Express + SQLite 权威后端 + JWT 登录。开箱、计时和库存由自建服务端计算，详见主策划案第九至第十一节。
- **远期目标**：替换为本文的三端隔离架构，由 Steamworks 负责身份和资产，PlayFab 负责云端校验和数据存储，Photon 负责轻量实时消息，以降低自建服务器的运维和成本。
- 切换时间和迁移步骤待定。在正式切换之前，新功能仍按当前的 Node.js 流程开发；服务端业务逻辑尽量保持独立、可移植，方便以后迁到 CloudScript。

## 二、设计目标

在“防止玩家修改资产”和“服务器零成本或低成本”之间取平衡：

- 玩家能拿去交易、展示或影响他人的东西（资产、公会数据），必须由云端裁判。
- 只影响玩家自己画面的东西（动画、显示数值），交给客户端计算，换来零延迟的流畅体验。

## 三、三端分工

### 1. 客户端：Unity PC 端（主导过程与体验）

- **职责**：负责所有华丽的开箱动画、战力数值的实时计算、UI 交互和音效表现。
- **优势**：开发效率高，玩家操作零延迟。即使玩家用 CE 改了本地显示的战力也无所谓，这只是“前端自嗨”，不会影响任何权威数据。

### 2. 资产端：Steamworks（把控经济命脉与身份）

- **职责**：负责权威的资产增减和身份验证。
- **身份验证**：客户端生成 `Steam Auth Session Ticket`，防止接口被脚本滥用。
- **资产管理**（若接入 Steam Inventory）：掉落盲盒、销毁物品等指令由 Steam 服务器完成验证。

### 3. 校验与社交端：PlayFab + Photon（轻量级云端裁判）

#### PlayFab（BaaS）

- **公证处**：通过 CloudScript 云函数处理需要防作弊的关键结算，例如开箱结果和盲盒产出计时。云端读取玩家数据并计算结果，防止本地修改器作弊。
- **数据库**：存储玩家的展柜布局数据等云端数据。
- **安全防护**：使用微软自带的高防，并配置 API 限流（Rate Limiting），防止恶意刷包。

#### Photon Chat

- 负责轻量的全服公共频道聊天、跑马灯广播和点赞事件推送。

## 四、与当前策划冲突的部分（暂不启用）

原方案中有几项依赖已从策划中移除的系统。这些内容只记录架构上能做到，目前不规划实现：

| 原方案内容 | 当前状态 |
| --- | --- |
| CloudScript 读取玩家装备计算战力 | 装备系统已移除，战力计算改为只基于史莱姆 CP |
| Photon 跑马灯广播 | 全服广播已移除 |
| Photon 全服聊天和点赞推送 | 依赖多人社交，暂不启用 |

## 五、迁移时需要确认的问题

- 是否接入 Steam Inventory。如果不接入，盲盒和史莱姆库存的权威存储应放在 PlayFab。
- 开箱和盲盒产出计时是否改由 CloudScript 执行，以保持“随机结果由云端决定”的原则。
- 现有 SQLite 中的玩家数据（库存、图鉴、盲盒仓库）如何迁到 PlayFab。
- PlayFab 和 Photon 的免费额度能否覆盖预期玩家规模，以及超出后的计费方式。
