# 游戏后端与本地存档

> 状态：已实现（开发阶段方案）；正式版将替换为 PlayFab + Steam 权威后端  
> 最后更新：2026-11-06  
> 主策划入口：[《史莱姆盲盒》项目策划案](../史莱姆盲盒-项目策划案.md)  
> 关联代码：`Assets/Scripts/Backend/`（程序集 `SlimeBlindBox.Backend`）、`Assets/Scripts/App/GameBackendFactory.cs`、`Assets/Scripts/App/JsonFilePlayerDataStore.cs`、`Assets/Scripts/App/SlimeGameController.cs`、`Assets/Tests/EditMode/`  
> 关联文档：[目标后端架构](目标后端架构.md)、[品质与抽取系统](品质与抽取系统.md)、[盲盒产出与仓库系统](盲盒产出与仓库系统.md)

## 一、决策与范围

- 开发阶段所有玩法功能由客户端本地处理，原 Node.js + Express + SQLite 自建服务端已整体删除（2026-11-06，用户决定）。
- 正式版后端为 Steamworks + 微软 PlayFab（见 [目标后端架构](目标后端架构.md)）。本方案的目标是让切换时的改动只集中在“新增一个后端实现类 + 修改工厂”，界面、控制器和数据结构不变。
- 本地实现期间，玩家数据可以被本机修改，不具备防作弊能力。这是开发阶段接受的已知风险，正式发售前必须切换到权威后端（已列入上线阻塞项）。

## 二、分层结构

| 层 | 位置 | 职责 |
| --- | --- | --- |
| 后端接口 | `Backend/IGameBackend.cs` | 登录、游戏状态、领取、开箱、背包、图鉴、GM 的统一入口，全部以回调返回结果 |
| 数据结构 | `Backend/BackendModels.cs` | 返回给客户端的 DTO，字段名沿用原接口 JSON，未来与 CloudScript 返回结构一致 |
| 平衡配置 | `Backend/GameBalanceConfig.cs` | 品质、盲盒、史莱姆目录、产出间隔、成长公式，并提供配置校验 |
| 本地实现 | `Backend/Local/LocalGameBackend.cs` | 开发阶段的后端：本机计算产出、随机抽取、库存与图鉴 |
| 存档 | `Backend/Local/PlayerSaveData.cs`、`App/JsonFilePlayerDataStore.cs` | 玩家存档结构与本地 JSON 读写 |
| 选择实现 | `App/GameBackendFactory.cs` | 创建当前使用的后端，切换后端只改这里 |
| 控制器 | `App/SlimeGameController.cs` | 调用后端、记录请求状态、通知界面刷新；不直接修改玩家数据 |

`SlimeBlindBox.Backend` 是不引用 UnityEngine 的纯 C# 程序集（asmdef 开启 `noEngineReferences`）。PlayFab CloudScript 支持 C# Azure Functions，规则代码可以基本原样迁移到云端，客户端和云端共用同一套配置与计算逻辑。

## 三、接口约定

| 方法 | 作用 | 主要失败码 |
| --- | --- | --- |
| `Login` | 读取或创建存档并修复异常值 | `LOAD_FAILED`、`SAVE_VERSION_TOO_NEW`、`CONFIG_INVALID` |
| `GetGameState` | 结算挂机产出，返回待领取数量、容量、间隔、总 CP、下一个盲盒时间和仓库 | `NOT_LOGGED_IN` |
| `ClaimBoxes` | 领取全部待领取盲盒，按产出时已确定的品质放入仓库 | `NO_PENDING_BOXES` |
| `OpenBox(key)` | 消耗 1 个指定品质盲盒，按加成后的权重抽取 1 只史莱姆 | `UNKNOWN_BOX_RARITY`、`BOX_STOCK_EMPTY` |
| `GetInventory` | 返回持有的史莱姆、等级与有效 CP | `NOT_LOGGED_IN` |
| `GetDictionary` | 返回全部图鉴条目、发现状态与完成度 | `NOT_LOGGED_IN` |
| `DebugModifyBoxes` | GM：增加、填满、清空待领取盲盒，推进计时 | `DEBUG_TOOLS_DISABLED`、`INVALID_ARGUMENT` |

- 任何修改操作失败都还会返回 `SAVE_FAILED` 或 `INTERNAL`。
- 失败时返回 `BackendError`：`code` 供程序判断，`message` 是可以直接展示的中文提示，集中在 `BackendMessages` 中，不包含异常堆栈等内部信息；异常细节只写入 Unity 日志。
- 回调可能同步也可能异步触发。控制器用请求计数判断“处理中”，处理中不会重复发起领取或开箱。

## 四、规则实现

规则与原服务端完全一致，详细数值见 [品质与抽取系统](品质与抽取系统.md) 和 [盲盒产出与仓库系统](盲盒产出与仓库系统.md)：

- 每 3 小时产出 1 个待领取盲盒，默认上限 8 个；达到上限后停止累计，并把计时基准推进到当前时间。新玩家初始有 1 个待领取盲盒。
- 每个盲盒在产出时按 白 45% / 绿 30% / 蓝 15% / 紫 8% / 红 2% 独立随机品质，存为 `pendingBoxRarities`，并以 `pending_boxes` 下发给凝聚台显示；领取时原样放入仓库。仓库无上限。
- 开箱按 `max(1, round(基础权重 × (1 + 加成)^(阶级 - 2)))` 调整权重后抽取一只史莱姆。
- 有效 CP = `floor(基础 CP × (1 + log2(等级) × 0.25)) × 数量`，总 CP 实时计算。
- 首次获得史莱姆时记录首次获得时间，用于图鉴。
- 随机数使用加密随机源，并用拒绝采样消除取模偏差。
- 系统时间被调回过去时，计时基准回退到当前时间，避免产出永久停滞。

## 五、存档

- 路径：`Application.persistentDataPath/save/player.json`，UTF-8 JSON，时间统一为 UTC Unix 毫秒。
- 结构：`schemaVersion`、玩家 ID 与昵称、待领取数量与品质列表、计时、盲盒仓库（按品质计数）、史莱姆记录（数量、等级、经验、首次获得时间）。记录存在即视为图鉴已解锁。
- `pendingBoxRarities` 为新增字段，未提升 `schemaVersion`：旧存档读取时由 `Normalize` 按领取概率补齐，数量不一致或品质键无效时自动修正，已有玩家数据不需要删档。
- 原子写入：先写 `player.json.tmp`，再用 `File.Replace` 替换正式文件，同时把上一份保留为 `player.json.bak`。
- 读取容错：主存档缺失或损坏时使用备份；两者都不可用时把损坏文件改名为 `player.json.corrupt-时间` 保留，然后创建新存档。
- 数据修复：登录时修正负数、空列表、重复条目和缺失的盲盒品质。
- 版本：存档 `schemaVersion` 高于当前游戏时拒绝读取并提示更新，防止旧版本覆盖新存档。以后的结构变更通过升级 `schemaVersion` 和迁移代码完成。
- 事务：每个修改操作在存档副本上执行，保存成功后才替换内存数据；保存失败时游戏状态保持不变并提示玩家。

## 六、开发者工具

- GM 由 `GameBackendFactory.DeveloperToolsEnabled` 统一控制。开发阶段按用户要求设为 `true`，Editor、Development Build 和正式打包的游戏都显示 GM 面板（2026-11-06 变更，原为仅开发构建可用）。
- 设为 `false` 时后端直接拒绝调用，界面也不显示 GM 面板。对外发售前必须改为 `false`（已列入上线阻塞项）。
- 增加数量范围 1～100，推进计时范围 1～168 小时。

## 七、迁移到 PlayFab + Steam 的步骤

1. 接入 Steamworks.NET（或 Facepunch.Steamworks），客户端获取 `GetAuthSessionTicket`，通过 PlayFab `LoginWithSteam` 登录。
2. 把 `GameBalanceConfig` 中的品质、盲盒和史莱姆目录迁移到 PlayFab Title Data / Catalog；客户端只读用于展示。
3. 把 `LocalGameBackend` 中的规则迁移为 CloudScript（C# Azure Functions），存档字段对应 PlayFab User Data 与 Inventory。
4. 新增 `PlayFabGameBackend : IGameBackend`，用 `ExecuteFunction` 调用云函数，返回现有 DTO；在 `GameBackendFactory` 中切换实现。
5. 提供一次性导入：把开发期本地存档迁移到 PlayFab（是否保留开发期进度待确认）。
6. 删除 Release 构建中的 `LocalGameBackend`，保留它作为离线测试和单元测试用实现（待确认）。

## 八、验收标准

- 项目中不存在自建服务端代码，启动游戏不需要运行任何本地服务。
- 新存档：1 个待领取盲盒、容量 8、间隔 3 小时；离线 48 小时后待领取为 8 个且显示“已满”。
- 领取、开箱、背包、图鉴、GM 功能与原服务端行为一致；关闭并重新启动游戏后数据保留。
- 背包条目除合计 `effective_cp` 外，还下发单只有效 CP `unit_effective_cp` 和等级加成倍率 `level_cp_multiplier`，供背包详情直接展示（字段说明见 [背包与物品界面](背包与物品界面.md) 第四节）。
- 存档损坏或保存失败时游戏不崩溃，并给出可理解的提示。
- EditMode 测试（`Assets/Tests/EditMode`，21 项）全部通过，覆盖产出结算、封顶、领取、开箱、库存不足、存档持久化、保存失败回滚、时间回拨、GM 范围与开关、脏数据修复、存档版本和配置校验。
